# 0001. Прагматичный модульный монолит с тактическим DDD

- Статус: accepted
- Дата: 2026-09-12
- Автор: architect
- Связанная задача: —

## Контекст

Проект молодой: один агрегат, сценарии в контроллере, DDD отсутствует.
Планируется рост: API/CLI, файлы, аккаунты, админка/аудит, burn-after-reading,
настраиваемый TTL. Целевой формат — open-source/self-hosted, один сервер,
возможная миграция с SQLite. Команда маленькая (человек + агенты).

## Рассмотренные варианты

1. **Оставить как есть** — быстро, но границы размываются, тестируемость и
   предсказуемость роста падают.
2. **Полноценная гексагональная архитектура + CQRS/ES** — максимальная
   изоляция, но существенный бойлерплейт и сложность для текущего масштаба.
3. **Прагматичный модульный монолит с тактическим DDD** — границы и домен без
   избыточной инфраструктуры; паттерны вводятся по мере пользы.

## Решение

Выбран вариант 3. Модульный монолит: команды в строках не выполняются, вместо
них — Symfony Messenger только для фоновых задач. Домены модулей изолированы от
фреймворка. Aгрегаты, VO, порты репозиториев и порты недетерминизма
применяются там, где защищают инварианты и улучшают тестируемость. Event
Sourcing, CQRS, sagas и микросервисы — отложены до появления явных триггеров
(см. `docs/ARCHITECTURE.md`, раздел 4.3).

## Последствия

- Проще: тесты домена без контейнера, замена СУБД, независимое развитие
  контекстов, понятные ревью.
- Сложнее: больше файлов на сценарий, нужен дептрек и дисциплина границ.
- Требуется миграция легаси-кода инкрементально, начиная с извлечения
  `CreateSecret`.
