# 007-extract-access-rate-limiting: выделение rate limiting в контекст `Access`

> Статус: **G1 пройден.** Объём — извлечение rate limiting из Presentation
> `Secret` в контекст `Access` (`docs/ARCHITECTURE.md` §3.1/§3.2) по образцу
> 002–006 **без изменения наблюдаемого поведения**: лимиты, политики, окна,
> ключи, тексты, порядок проверки, `422` через форму, хранилище `cache.app`,
> CSRF, `no-store`, маршруты и wire-контракты остаются прежними. Любое изменение
> лимитов/квот/семантики ошибок — вне 007 (см. «Вне объёма»).

## Контекст и проблема

Задачи 002–006 вынесли бизнес-сценарии (`CreateSecret`, `RevealSecret`, `Purge`,
`created`) в модуль `Secret`, удалили легаси-слой `App\*` и переименовали
таблицу `paste → secret` (ADR 0002–0004). Единственным, что осталось
«размазанным» по Presentation, оказалось лимитирование запросов:

- `src/Secret/Presentation/Http/CreateSecretController.php:15,21,28-31` —
  контроллер принимает конкретный `Symfony\Component\RateLimiter\RateLimiterFactory`
  `$createPasteLimiter`, строит ключ `getClientIp() ?? 'unknown'` и вызывает
  `->create($ip)->consume()->isAccepted()`;
- `src/Secret/Presentation/Http/RevealSecretController.php:19,30,42-44` — то же
  для `$unlockPasteLimiter` с ключом `(getClientIp() ?? 'unknown').':'.$token`;
- bindings `config/services.yaml:10-11` (`@limiter.create_paste` /
  `@limiter.unlock_paste`) и политики `config/packages/rate_limiter.yaml:3-11`
  (`fixed_window`, `limit: 10`, `interval: 1 minute`, `cache_pool: cache.app`).

`docs/ARCHITECTURE.md` §3.1 относит `Access` к supporting-контекстам и
закрепляет за ним «лимиты, квоты, защита от перебора»; §3.2 уже предусматривает
каталог `src/Access/`, но в коде его нет. Из-за прямой зависимости Presentation
от инфраструктурного класса Symfony модуль `Secret` знает о конкретной
реализации лимитирования, граница контекста не выделена и не проверяется
deptrac. При этом 007 — последняя миграционная задача перед 008
(`finalize-architecture-docs`), поэтому контекст `Access` должен появиться
именно здесь (ARCHITECTURE §3.1: модуль создаётся, когда под него есть задача).

**Всеобъемлющее ограничение.** Наблюдаемое поведение лимитов сохраняется
байт-в-байт и статус-в-статус. Любое отклонение (другой ключ, окно, число
попыток, текст, статус `429`, иной момент `consume`) — триггер эскалации и
отдельный вопрос, а не часть 007.

## Пользовательская цель

Как мейнтейнер/разработчик CopyPaste, я хочу, чтобы механизм лимитирования жил
в отдельном контексте `Access` за framework-free портом, а Presentation модуля
`Secret` только сообщал «израсходуй одну попытку для лимита X по ключу Y», чтобы:

- `Secret` перестал зависеть от `Symfony\Component\RateLimiter` и имён
  лимитеров, а граница `Access` проверялась deptrac;
- поведение лимитов стало зафиксировано тестами на уровне порта/адаптера и
  осталось неизменным на HTTP-уровне;
- будущие задачи про квоты/аккаунты (`Identity`, `Quota`) имели готовую точку
  расширения, не задевая сценарии `Secret`.

Как получатель ссылки, я хочу, чтобы защита от перебора работала ровно как
раньше: те же лимиты, те же тексты, тот же `422`, те же правила расхода.

## Текущее поведение лимитов (as-is, эталон для 007)

Проверено по коду, конфигам и существующим тестам.

| Аспект | Как сейчас |
|---|---|
| Лимиты и политика | `create_paste` и `unlock_paste`: `policy: fixed_window`, `limit: 10`, `interval: '1 minute'`, `cache_pool: cache.app` (`config/packages/rate_limiter.yaml`) |
| DI | `$createPasteLimiter: '@limiter.create_paste'`, `$unlockPasteLimiter: '@limiter.unlock_paste'` (`config/services.yaml`) |
| Create: ключ | `$request->getClientIp() ?? 'unknown'` (лимит на IP) |
| Create: момент consume | внутри `if ($form->isSubmitted())`, **до** `$form->isValid()`; `GET` (форма не отправлена) лимит не расходует; невалидные и неверные CSRF-отправки расходуют |
| Create: исчерпание | root-ошибка формы `FormError('Слишком много запросов. Попробуйте через минуту.')`; создание не вызывается, запись не появляется |

| Reveal: порядок | `LoadRevealSecret` → `404` для «нет/истекло» **до** лимита; затем при `isSubmitted()` consume **до** валидации; далее валидация, затем `RevealSecret` |
| Reveal: расход | «нет/истекло» (`404`) лимит не расходует; невалидный/пустой ключ расходует; 11-я отправка даже с верным ключом — отклоняется лимитом, расшифровка не выполняется |

| Тексты | Create и Reveal — **разные** (см. выше), сохраняются дословно |
| Хранилище | окно живёт в `cache.app`; тесты изолируют его `cache.app->clear()` в `setUp()` (`CreateSecretFlowTest`, `RevealSecretFlowTest`, `PasteFlowTest`) |

Классов/каталога `src/Access` сейчас нет; тестов на лимитер в изоляции от HTTP
тоже нет — только functional.

## Объём (in scope)

1. **Создание контекста `Access`** в целевой структуре §3.2: `src/Access/Domain`
   (framework-free контракт лимитирования) и `src/Access/Infrastructure`
   (адаптер поверх Symfony RateLimiter). Состав минимальный, по §4.2: не
   плодить VO/слои без инвариантов.
2. **Порт лимитирования.** Контракт, который позволяет «израсходовать одну
   попытку для именованного лимита по строковому ключу» и вернуть
   `accepted`/`rejected`. Порт не импортирует Symfony, Doctrine, Sodium; имя и
   точная форма (например, `RateLimiter`/`AccessPolicy`) — решение архитектора,
   требования фиксируют только семантику.
3. **Адаптер `Access/Infrastructure`** поверх существующих
   `framework.rate_limiter`-фабрик `create_paste`/`unlock_paste` и `cache.app`.
   `Symfony\Component\RateLimiter` допускается только здесь.
4. **Интеграция в Presentation `Secret`** вместо прямого `RateLimiterFactory`:
   контроллеры формируют ключ и текст ошибки как сейчас и вызывают порт в том
   же месте/порядке (create: до валидации; reveal: после `404`, до валидации).
   Импорт `Symfony\Component\RateLimiter\RateLimiterFactory` из
   `Secret/Presentation` удаляется.
5. **Конфигурация.** `config/packages/rate_limiter.yaml` сохраняет обе фабрики
   и все значения (`fixed_window`, `10`, `1 minute`, `cache.app`);
   `config/services.yaml` связывает порт с адаптером и передаёт ему фабрики.
   Новые env-параметры не вводятся, значения не дублируются.
6. **deptrac.** Добавить слои `Access_Domain`/`Access_Infrastructure` и правила,
   разрешающие `Secret_Presentation → Access_Domain` и адаптеру — Symfony;
   запретить `Secret_Domain`/`Secret_Application` → `Access_*` и
   `Secret_*` → `Access_Infrastructure`. `make deptrac` — 0 нарушений.
7. **Тесты.** Unit/integrationного уровня тесты порта/адаптера (принятие/
   отклонение, независимость лимитов и ключей), wiring-тест контейнера и
   конфигурации лимитов; существующие functional-тесты сохраняются **без
   изменения ожиданий** (допускаются только технические правки: imports,
   получение порта из контейнера, изоляция окна).
8. **Документы задачи:** этот `requirements.md`; далее `plan.md`/`review.md`.

## Доменные термины (новые/уточнённые)

**Новых доменных терминов нет; `docs/UBIQUITOUS_LANGUAGE.md` не изменяется.**

- `Access` — имя архитектурного bounded context (`ARCHITECTURE.md` §3.1/§3.2),
  а не предметный термин. Контексты (`Crypto`, `Shared`) в глоссарий не
  заводятся, поэтому `Access` туда не добавляется.
- `Rate limiting` / `Rate limit` — техническое имя механизма защиты от
  перебора; в глоссарии нет и не требуется: пользовательского доменного
  значения у него нет, а описание целиком живёт в `ARCHITECTURE.md` §3.1.
- `AccessPolicy`/`RateLimiter` — технические имена порта/адаптера, композиции
  существующих понятий; в глоссарий не идут.
- Существующие термины (`Secret`, `SecretKey`, `Token`, `Reveal`,
  `Burn-after-reading`, `Purge`) не переопределяются и не расширяются.

## Открытые вопросы (и ответы человека)

> Статус G1: **пройден.** Решения Q1–Q6 = A (см. «Решения, утверждённые на G1»).
> Ответы фиксируются в таблице в конце раздела.

### Q1 (блокирующий). Где вызывается порт `Access`: Presentation или Application?

Требование «сохранить наблюдаемое поведение» конкурирует с формулировкой
`ROADMAP.md` §007 «интеграция в use case'ы». Разберём по порядку проверок:

- **A (рекомендую). Порт вызывается из Presentation.** `Access/Domain` —
  опубликованный framework-free порт, `Access/Infrastructure` — Symfony-адаптер,
  контроллеры `CreateSecretController`/`RevealSecretController` зависят от порта
  и вызывают `consume` ровно там, где сейчас. *Плюсы:* порядок «до валидации»,
  ключи `ip` / `ip:token`, тексты и `422` воспроизводятся байт-в-байт;
  `Secret/Application` не знает о HTTP-идентичности клиента (IP/токен);
  `RateLimiterFactory` уходит из `Secret/Presentation`; границы модулей
  соблюдены (§3.3: между модулями виден опубликованный доменный порт).
  *Минусы:* формально `ROADMAP.md` говорит «в use case'ы» — формулировку надо
  уточнить (см. Q2), фактически вызов происходит в HTTP-сценарии.
- **B. Порт вызывается из Application use case (`CreateSecret`/`RevealSecret`).**
  *Минус-блокер:* сценарии сейчас расходуют лимит **до** валидации формы и
  **после** `404`-гейта Reveal. Чтобы это сохранить, контроллер всё равно
  обязан вызвать лимит до валидации; если же лимит станет шагом use case,
  изменится наблюдаемое: невалидные/пустые отправки перестанут расходовать
  лимит (валидация выполняется раньше), а Create-контроллеру придётся
  валидировать до вызова use case — 11-я невалидная отправка начнёт давать
  ошибку валидации вместо ошибки лимита. Кроме того, use case получил бы
  `clientIp`/`token` как транспортный параметр, а `Secret_Application` —
  зависимость от `Access`. Требование «поведение неизменно» делает B
  неприемлемым без смены семантики.
- **C. Не выносить, оставить `RateLimiterFactory` в контроллерах.** Противоречит
  цели 007 и `ARCHITECTURE.md` §3.1/§3.2; контекст `Access` не появляется.
  Отклоняется.

**Рекомендация:** **A.** `Domain`/`Application` модуля `Secret` не должны знать
о лимитах; лимит — это входящая защита HTTP-сценария.

### Q2. Как трактовать формулировку `ROADMAP.md` «интеграция в use case'ы»?

- **A (рекомендую).** В 007 «use case» = «пользовательский сценарий», а не
  класс `Application`. Порт вызывается в Presentation, потому что только это
  сохраняет порядок «consume до валидации / после 404». Считать 007 исполнением
  §3.1; в задаче 008 уточнить формулировку `ROADMAP.md` при финализации
  документов (правка roadmap — в 008, не в 007).
- **B.** Понять буквально и перенести вызов в `Application`. Тогда требуется
  отдельное решение человека о **смене наблюдаемого поведения** (порядок,
  расход невалидных отправок, возможно отказ от `422` в пользу иного ответа) —
  это отдельный триггер, выходящий за инвариант 007. Не рекомендую.

### Q3. Форма контракта и работа с двумя лимитами

- **A (рекомендую).** Один минимальный framework-free порт с операцией
  «consume(лимит, ключ) → accepted/rejected»; лимиты `create_paste`/
  `unlock_paste` остаются двумя **именованными** конфигурациями Symfony,
  адаптер получает их из `config/services.yaml`. Ключ и текст ошибки формирует
  Presentation. Никаких VO/политик, пока нет инвариантов (§4.2).
- **B.** Два отдельных порта (по одному на лимит) / отдельные сервисы. Чище по
  типам, но плодит дублирование и усложняет добавление квот; допустимо на
  усмотрение архитектора.
- **C.** Порт повторяет API Symfony (`create($key)->consume()`), т.е.
  протекает деталь реализации в `Access/Domain`. Отклоняется.

Точные имена (`RateLimiter`, `AccessPolicy`, …) и сигнатуры — решение
архитектора на G2; требования фиксируют семантику и запрет на Symfony в
`Access/Domain`.

### Q4. Нужен ли ADR и как менять deptrac?

- **A (рекомендую).** **ADR не нужен.** Создание контекста `Access` — прямое
  исполнение `ARCHITECTURE.md` §3.1/§3.2, а не изменение стандарта. Deptrac
  дополняется слоями `Access_Domain`/`Access_Infrastructure` и правилами
  (AC7); это исполнение уже принятой архитектуры, не новый стандарт.
- **B.** Короткий ADR про границу `Access` и направление зависимости
  (`Secret_Presentation → Access_Domain`). Плюс — явная фиксация; минус —
  дублирует §3.1/§3.2 и без нужды расширяет задачу. Допустимо, если человек
  хочет письменно закрепить именно интеграцию из Presentation.
- **C.** Не описывать слои в deptrac. Отклоняется: границы должны проверяться
  автоматически (§3.3).

**Рекомендация:** A (ADR не требуется). Если G1 выберет Q1-B, потребуется ADR
о смене поведения/границ — это отдельный триггер.

### Q5. Объём тестов и правок существующих тестов

- **A (рекомендую).** Добавить тесты порта/адаптера (принятие/отклонение,
  независимость лимитов и ключей) и wiring/конфиг-тест; existing functional
  оставить с прежними ожиданиями, допустив только технические правки
  (imports, получение порта, изоляция `cache.app`). Дополнительно — негативный
  структурный guard, что `Symfony\Component\RateLimiter` не встречается вне
  `Access/Infrastructure`.
- **B.** Перенести проверки порядка `consume` в unit-тесты Presentation (с
  фиктивным портом), чтобы зафиксировать «consume до валидации» без HTTP.
  Полезно, но HTTP-тесты уже это покрывают; можно как дополнение.
- **C.** Ограничиться существующими functional-тестами, не добавляя тестов
  `Access`. Отклоняется: контекст останется непокрытым, а порог покрытия
  `src/*/Domain` может не выполниться.

### Q6. Подтверждение сохранения лимитов и границ out-of-scope

- **A (рекомендую).** Зафиксировать: лимиты 10/1 мин, политика `fixed_window`,
  `cache.app`, ключи `ip` и `ip:token`, тексты, `422`, порядок проверки

- **B.** Разрешить в 007 любое из перечисленного — требует отдельного
  решения человека и меняет наблюдаемое поведение; не рекомендую.

## Нефункциональные требования и риски

### Нефункциональные требования

- **Неизменность поведения.** Лимиты, политики, окна, ключи, тексты, статусы
  (`422`, не `429`), порядок `consume`, `cache.app` и существующие
  functional/wiring-контракты не меняются; изменение любого из них — отдельный
  вопрос/триггер.
- **Безопасность.** Запрещено логировать/хранить `plaintext`, `SecretKey`,
  производные ключи, `salt/nonce`; лимиты не ослабляются и не отключаются;
  CSRF, `Cache-Control: no-store` и проверка срока не затрагиваются; контекст
  `Access` не получает доступа к payload/секретам (только строковый ключ и имя
  лимита); `.env.local` не добавляется.
- **Границы слоёв.** `Access/Domain` не зависит от фреймворка; `Access` не
  импортирует `Secret`/`Crypto`; `Secret/Domain` и `Secret/Application` не
  зависят от `Access`; `Secret/Presentation` зависит только от порта
  `Access/Domain`; deptrac 0 нарушений.
- **Конфигурация.** Единственный источник значений лимитов —
  `config/packages/rate_limiter.yaml`; привязка — `config/services.yaml`; без
  дублирования в env-параметрах и без хардкода в `Domain`.
- **Тестируемость.** Порт подменяется фиктивной реализацией; адаптер
  проверяется на детерминированном хранилище; HTTP-поведение — существующими
  functional-тестами; изоляция окна — через `cache.app` в `setUp()`.
- **Производительность.** На запрос добавляется одна операция обращения к
  кешу лимитера (как сейчас); новых обращений к БД/сети нет.
- **Совместимость.** PHP 8.4, Symfony 7.4 (`framework.rate_limiter`),
  `cache.app`; миграций и изменений схемы нет.
- **Обозримость diff.** Изменения локальны (`src/Access`, два контроллера,
  `config/services.yaml`, `deptrac.yaml`, тесты); `src/Secret/Domain`,
  `Application`, шаблоны, миграции, публичные имена не трогаются.

### Риски

| Риск | Влияние | Мера |
|---|---|---|
| Смена порядка `consume` относительно `404`/валидации | Иное наблюдаемое поведение, ослабление защиты | Q1-A: вызов порта из Presentation на прежнем месте; AC4 и существующие functional-тесты без смены ожиданий |
| Изменение ключа (`ip` / `ip:token`) или текста | Регресс лимитов/UX | AC2/AC3/AC6: точные ключи и тексты; те же тесты |
| Перенос вызова в Application (Q1-B) | Невалидные отправки перестают расходовать лимит; меняется код ошибки | Явный триггер эскалации; рекомендация A; без решения человека не реализуется |
| Протечка Symfony RateLimiter в `Secret`/`Access/Domain` | Нарушение границ, непроверяемость | AC1/AC7: Symfony только в `Access/Infrastructure`; structural guard и deptrac |
| Смена `cache.app` на другой пул | Ломается изоляция тестов и поведение окна | AC5: `cache_pool: cache.app` сохраняется |
| Дублирование значений лимитов в env/коде | Дрейф конфигурации | AC5: единственный источник — `rate_limiter.yaml` |
| Слишком «толстый» `Access` (VO/политики без инвариантов) | Преждевременная сложность (§4.2) | Q3-A: минимальный порт; решение об именах/форме — G2 |
| Флейки тестов из-за общего окна | Нестабильный `make qa` | Существующая изоляция `cache.app->clear()`; адаптер-тесты — на изолированном хранилище |
| Падение покрытия `src/*/Domain` | Красный `make coverage` | AC8: тесты порта/адаптера; при отсутствии исполняемого кода в `Access/Domain` порог не страдает |

| Устаревание формулировки `ROADMAP.md` о «use case'ах» | Расхождение документов и кода | Q2-A: уточнение в 008; в 007 решение фиксируется в plan/review |
