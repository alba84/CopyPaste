# 009-secret-key-visibility: показ секретного ключа по удержанию иконки «глаз»

> Статус: **G1 пройден** — человек подтвердил все варианты A (Q1–Q10).
> Код, шаблоны и стили в рамках этой задачи не меняются — только артефакты
> аналитика.
>
> Постановка человека (дословно): «поле ввода секретного ключа нужно сделать
> доступным для просмотра с помощью иконки "глаз", чтобы при нажатии и
> удержании иконки было видно что написано в поле. При отпускании иконки нужно
> снова прятать секретный ключ.»

## Контекст и проблема

`SecretKey` — единственный секрет, который пользователь вводит сам, и сервер
его не хранит: ключ используется только для шифрования при создании записи и
для расшифровки при `Reveal`. Опечатка в ключе при создании делает `Secret`
нерасшифровываемым даже для получателя с «правильным» ключом, а при вводе на
странице `/p/{token}` даёт нейтральную ошибку без возможности исправить ввод
иным способом, кроме повторного набора. `docs/tz/1-tz-copypaste.md` фиксирует,
что ключ не сохраняется и не логируется, а его длина — до 255 символов; эти
ограничения задачей не меняются.

Сейчас оба поля — `PasswordType`:

- создание: `src/Secret/Presentation/Http/Form/CreateSecretType.php`, поле
  `secret` (`create_paste[secret]`, `autocomplete=new-password`);
- выдача: `src/Secret/Presentation/Http/Form/RevealSecretType.php`, поле
  `secret` (`unlock_paste[secret]`, `autocomplete=current-password`).

Оба поля выводятся через `form_row` в `templates/paste/create.html.twig` и
`templates/paste/view.html.twig`. Кастомной формы-темы для парольных полей нет
(`config/packages/twig.yaml` использует стандартный
`form_div_layout.html.twig`), иконки/слота под неё в разметке нет. Стили полей
— `public/styles/app.css` (`.input`, `.field`), клиентский JS — только
`public/copy.js` (копирование ссылки и счётчик символов).

Пользователь не может проверить набранный ключ перед отправкой. Нужен
локальный, чисто клиентский способ кратковременно показать значение поля,
минимизируя риск «подсматривания»: ключ виден только пока пользователь
удерживает элемент управления, и снова маскируется при отпускании.

## Пользовательская цель

Отправитель и получатель могут убедиться, что ключ набран без опечаток, не
покидая форму и не отправляя данные:

- нажать и удерживать иконку «глаз» — значение `SecretKey` видно в поле;
- отпустить иконку (или прервать взаимодействие) — значение снова скрыто;
- то же самое доступно с клавиатуры и через скринридер, без мыши и без
  обязательного «удержания» для пользователей assistive technology;
- поведение формы, серверная логика, криптография и схема БД не меняются.

Успех: пользователь может проверить ключ до отправки, при этом ключ не остаётся
видимым после завершения взаимодействия и никуда не передаётся и не
логируется.

## Объём (in scope)

1. **Оба поля `SecretKey`**: создание (`/`, `create_paste[secret]`) и выдача
   (`/p/{token}`, `unlock_paste[secret]`). Одинаковое поведение и внешний вид.
2. **Один переиспользуемый элемент управления** (кнопка с иконкой «глаз»)
   внутри поля ввода, справа; единый источник разметки для обеих форм, без
   копирования разметки иконки в `create.html.twig` и `view.html.twig`.
3. **Клиентское переключение видимости**: значение поля отображается/маскируется
   без изменения `value`, без отправки формы и без перезагрузки страницы.
   Серверный HTML поля остаётся `type="password"`; видимость меняется только в
   рантайме.
4. **Сценарий press-and-hold для указателя** (мышь/перо/палец): нажатие —
   показать, отпускание — скрыть. Скрытие также при любом прерывании:
   уход указателя с элемента, `pointercancel`, потеря захвата указателя, потеря
   фокуса элементом, уход страницы в фон, `Escape`.
5. **Touch-специфика**: длительное нажатие не должно вызывать контекстное меню,
   выделение текста/лупу, случайную отправку формы; страница должна оставаться
   прокручиваемой; уход пальца/скролл скрывают ключ.
6. **Клавиатура и accessibility**: элемент достижим `Tab`, имеет видимый
   focus-ring, доступное имя на русском, отражает состояние видимости
   (`aria-pressed`), связан с полем (`aria-controls`); иконка декоративна для
   скринридера. Клавиатурная/AT-активация работает без «удержания» (см. Q3).
7. **Визуальные состояния**: обычное, hover, нажатое (иконка «перечёркнутый
   глаз»), focus-visible; курсор-указатель; tooltip не является единственным
   носителем смысла.
8. **Прогрессивное улучшение**: без JS (или при ошибке скрипта) поле остаётся
   скрытым, форма работает, «мёртвая» кнопка не показывается.
9. **Тесты и проверка**: functional-тесты на разметку и неизменность контрактов;
   ручной чек-лист для pointer/touch/клавиатуры/скринридера и браузерной
   матрицы (JS-тестовой инфраструктуры в проекте нет).
10. **Документация**: новый UI-термин в `docs/UBIQUITOUS_LANGUAGE.md` (см.
    раздел «Доменные термины»).

## Доменные термины (новые/уточнённые)

Существующие термины используются без изменения значений:

- **SecretKey** — вводимый пользователем ключ, сервером не хранится.
- **Reveal** — успешная расшифровка и показ `Plaintext`. **Для этой задачи
  термин `Reveal` не используется**: показ значения поля с ключом — это не
  расшифровка и не показ `Plaintext`, смешивать нельзя.
- **Hint**, **Plaintext**, **Token** — не затрагиваются.

Новый термин (UI, не доменный инвариант):

- **Secret key visibility toggle** — элемент управления в поле `SecretKey`,
  который показывает значение ключа, пока пользователь удерживает его
  указателем, и/или переключает видимость при клавиатурной/AT-активации; при
  отпускании, потере фокуса или ином прерывании значение снова маскируется.
  В коде/классах/атрибутах использовать терминологию `SecretKey`
  (`secret-key-visibility`), а не `password`/`paste`.

Микрокопия доступного имени (фиксируется в требованиях, не новый термин):

- скрытое состояние: «Показать секретный ключ»;
- видимое состояние: «Скрыть секретный ключ».

`docs/UBIQUITOUS_LANGUAGE.md` дополняется строкой `Secret key visibility
toggle`; существующие значения не меняются.

## Критерии приёмки (Given–When–Then)

> AC1 и AC11 проверяются functional-тестами и `make qa`; AC9 — ревью diff;
> AC7 и AC10 — ручным/инструментальным чек-листом (DOM, CSS, сеть, консоль,
> storage); AC2–AC6, AC8 и AC12 — браузерным чек-листом и ревью (JS-тестовой
> инфраструктуры в проекте нет). Формулировки AC2/AC4/AC5 зависят от решений
> Q3/Q4.

**AC1 — оба поля содержат элемент управления; серверный HTML остаётся
парольным.**
Given страницы `GET /` и `GET /p/{валидный токен}`;
When разбирается серверный HTML;
Then на каждой странице ровно одно поле
`input[type="password"][name="create_paste[secret]"]` /
`input[type="password"][name="unlock_paste[secret]"]` с неизменными
`maxlength="255"` и `autocomplete` (`new-password` / `current-password`), и
ровно один элемент управления `button[type="button"]` с атрибутом
`data-secret-key-visibility`, `aria-controls`, равным `id` поля,
`aria-label="Показать секретный ключ"`, `aria-pressed="false"`, иконкой
`aria-hidden="true"`; в серверном HTML кнопка имеет атрибут `hidden`
(включается JS).

**AC2 — удержание указателя показывает ключ, отпускание скрывает.**
Given поле содержит значение `K`, страница загружена с работающим JS;
When пользователь нажимает и удерживает элемент управления указателем;
Then `input.type === 'text'`, `aria-pressed="true"`,
`aria-label="Скрыть секретный ключ"`, значение поля остаётся `K`, форма не
отправляется, фокус ввода остаётся в поле (Q4-A);
When отпускает указатель на элементе;
Then `input.type === 'password'`, `aria-pressed="false"`,
`aria-label="Показать секретный ключ"`, значение поля по-прежнему `K`.

**AC3 — любое прерывание скрывает ключ.**
Given ключ виден (AC2);
When происходит любое из: уход указателя за пределы элемента,
`pointercancel`, потеря захвата указателя, потеря фокуса элементом, уход
страницы в фон (`visibilitychange` → hidden), `Escape`;
Then поле снова `type="password"`, `aria-pressed="false"`, доступное имя
«Показать секретный ключ», значение не изменилось, навигации/отправки формы
нет.

**AC4 — touch-устройства: длительное нажатие без побочных эффектов.**
Given мобильный браузер (iOS Safari, Android Chrome);
When пользователь нажимает и удерживает элемент управления пальцем;
Then ключ виден; контекстное меню, выделение текста, «лупа»/callout не
появляются; форма не отправляется; страница остаётся прокручиваемой;
When пользователь уводит палец с элемента, начинает скролл или отпускает палец;
Then ключ скрыт; «залипания» видимого состояния нет.

**AC5 — клавиатура и скринридер.**
Given элемент управления достижим `Tab` и имеет видимый focus-ring;
When пользователь активирует его с клавиатуры (`Space`/`Enter`) по модели
Q3-A (переключение);
Then первый аккорд показывает ключ, повторный — скрывает;
`aria-pressed` и доступное имя меняются соответственно; фокус остаётся на
элементе; форма не отправляется; при `Escape`/потере фокуса ключ скрыт;
When пользователь скринридера активирует элемент (программный click);
Then переключение работает, имя и состояние (`pressed`/`not pressed`)
озвучиваются; иконка не создаёт лишнего объявления.

**AC6 — прогрессивное улучшение.**
Given JS отключён или скрипт не загрузился/упал;
When страница отображается;
Then поле остаётся `type="password"`, форма создаётся и отправляется как
раньше, элемент управления не виден (атрибут `hidden` не снят), «мёртвой»
кнопки нет, вёрстка не ломается.

**AC7 — визуально иконка внутри поля, без перекрытия текста.**
Given обе страницы на ширине 360 px и на десктопе;

## Открытые вопросы (и ответы человека)

> Рекомендации аналитика — вариант **A** в каждом вопросе, если не указано
> иное. Ответы фиксируются в таблице в конце раздела на G1.

### Q1 — оба ли поля входят в объём

- **A (рекомендую).** Оба: создание (`/`) и выдача (`/p/{token}`).
  Пользовательская проблема одинакова: опечатка в ключе необратима. Один
  переиспользуемый элемент управления снижает стоимость реализации и
  гарантирует одинаковое поведение.
- **B.** Только выдача: там ошибка видна сразу (нейтральный отказ), а при
  создании ключ вводится осознанно. Минус: при создании опечатка приводит к
  нерасшифровываемой записи, то есть проблема острее; поведение форм
  становится непоследовательным.
- **C.** Только создание. Минус: получатель тоже может ошибиться, а ключ
  вводится вручную.

**Вопрос к человеку:** подтверждаем A (оба поля)?

### Q2 — поведение на touch/указателе

- **A (рекомендую).** Строго press-and-hold: `pointerdown` — показать;
  `pointerup`, `pointerleave`, `pointercancel`, потеря захвата, уход страницы
  в фон, `Escape` — скрыть. Подавлять контекстное меню и выделение только на
  время взаимодействия с элементом; не блокировать прокрутку страницы;
  `touch-action` не должен запрещать pan-жесты.
- **B.** Tap-to-toggle на touch (нажал — показал, нажал — скрыл).
  Минус: ключ остаётся видимым дольше, чем нужно, и противоречит постановке
  «при отпускании снова прятать»; выше риск подсматривания.
- **C.** Игнорировать touch, оставить только мышь. Минус: мобильные
  пользователи — значимая доля; не выполняет постановку.

**Вопрос к человеку:** подтверждаем A (строгое удержание, скрытие при любом
прерывании, прокрутка не блокируется)?

### Q3 — клавиатура и accessibility (Space/Enter, `aria-pressed`, скринридер)

- **A (рекомендую).** Указатель — удержание (Q2-A). Клавиатура и
  assistive technology — **переключение**: `Space`/`Enter` (и программный
  `click` от скринридера) показывают ключ, повторная активация скрывает;
  `Escape` и потеря фокуса скрывают. `aria-pressed` отражает видимость,
  `aria-label` меняется между «Показать секретный ключ» и «Скрыть секретный
  ключ». Причина: «удержание» недоступно части пользователей switch/voice
  control и неудобно скринридеру; переключение — предсказуемая и проверяемая
  альтернатива при сохранении requested-поведения для указателя.
- **B.** Везде удержание, включая `Space`/`Enter` (`keydown` — показать,
  `keyup` — скрыть), а программный `click` от AT — переключение. Минус:
  сложнее и менее доступно; риск «залипания» при потере `keyup`.
- **C.** Везде переключение, включая мышь/палец. Минус: не выполняет
  постановку и увеличивает время видимости ключа.

**Вопрос к человеку:** подтверждаем A (pointer — hold, keyboard/AT — toggle,
сброс на blur/Escape)?

### Q4 — потеря фокуса, уход курсора, `pointercancel`, фокус поля

- **A (рекомендую).** Скрывать ключ при: уходе указателя с элемента,
  `pointercancel`, потере захвата, потере фокуса элементом, уходе страницы в
  фон, `Escape`. **Не скрывать по потере фокуса самим полем ввода** (иначе
  нажатие иконки, которое может увести фокус, сразу скроет ключ). Нажатие
  мышью/пальцем не должно уводить фокус из поля и менять позицию каретки —
  пользователь может продолжить ввод; при этом кнопка остаётся достижимой
  `Tab` для клавиатуры. Значение и `selectionStart/End` не меняются.
- **B.** Разрешить фокусу уходить на кнопку; скрывать только по `pointerup`.
  Минус: после проверки ключа нужно снова кликать в поле; выше риск
  неожиданного поведения при клавиатуре.
- **C.** Скрывать по `blur` поля ввода. Минус: конфликтует с нажатием на
  иконку, ключ может скрыться в момент показа.

**Вопрос к человеку:** подтверждаем A (сохранять фокус/каретку в поле, скрывать
по прерываниям, не по `blur` поля)?

### Q5 — визуальные состояния, размещение, tooltip

- **A (рекомендую).** Иконка «глаз» справа внутри поля; в нажатом/видимом
  состоянии — «перечёркнутый глаз» и акцентный цвет; hover — умеренное
  затемнение/подсветка; focus-visible — существующий акцентный outline;
  курсор `pointer`; видимая область нажатия ≥40×40 px (рекомендуется 44×44),
  без уменьшения высоты поля; правый padding поля исключает перекрытие
  текста; tooltip/`title` не обязателен и не является единственным носителем
  смысла (смысл — в `aria-label`); без анимации или с уважением
  `prefers-reduced-motion`.
- **B.** Иконка рядом с полем (снаружи). Минус: визуально разрывает поле,
  хуже ассоциация «показать значение этого поля», больше риск перекрытия на
  узких экранах.
- **C.** Текстовая кнопка «Показать» под полем. Минус: занимает место,
  отличается от постановки «иконка глаз», хуже на мобильных.

**Вопрос к человеку:** подтверждаем A (внутри поля справа, eye/eye-off,
≥40×40, без обязательного tooltip)?

### Q6 — где размещать разметку и как не дублировать её в двух шаблонах

- **A (рекомендую).** Единый источник в Presentation: form-theme-блок для поля
  `SecretKey` (или эквивалентный переиспользуемый партиал/тип поля), который
  выводит input + кнопку; обе формы (`CreateSecretType`, `RevealSecretType`)
  остаются `PasswordType` и используют этот блок. Серверный HTML — всегда
  `type="password"`; `name`, `id`, `maxlength`, `autocomplete`, label и errors
  не меняются. Блок не должен «захватывать» произвольные будущие парольные
  поля без явного решения.
- **B.** Общий Twig-партиал, который оборачивает `form_row(form.secret)` и
  добавляет кнопку. Плюс: меньше вмешательства в form-темы. Минус: сложнее
  гарантировать, что кнопка визуально внутри поля и связана с `id`; риск
  дублирования обёртки label/errors.
- **C.** Продублировать разметку в `create.html.twig` и `view.html.twig`.
  Минус: дрейф, нарушает AC8; не рекомендую.

**Вопрос к человеку:** подтверждаем A (единый form-theme-блок/переиспользуемый
источник, поля остаются `PasswordType`)?

### Q7 — JS-модуль и прогрессивное улучшение

- **A (рекомендую).** Отдельный небольшой скрипт
  (`public/secret-key-visibility.js`, `defer`, без зависимостей), подключаемый
  в `base.html.twig`; один обработчик на все элементы
  `[data-secret-key-visibility]`. Кнопка в серверном HTML имеет `hidden`;
  скрипт снимает `hidden` и навешивает обработчики. Без JS/при ошибке поле
  остаётся скрытым, «мёртвой» кнопки нет. Без inline-JS и без изменения CSP.
- **B.** Добавить логику в существующий `public/copy.js`. Плюс: меньше файлов.
  Минус: смешение ответственностей, сложнее тестировать/отключать.
- **C.** Inline-скрипт в шаблоне. Минус: CSP, дублирование, плохая
  кешируемость; не рекомендую.

**Вопрос к человеку:** подтверждаем A (отдельный defer-скрипт, кнопка скрыта
без JS)?

### Q8 — браузеры и минимальные требования (Pointer Events vs fallback)

- **A (рекомендую).** Современные evergreen-браузеры: Chrome, Edge, Firefox,
  Safari — последние две версии; iOS Safari 15+; Android Chrome. Использовать
  Pointer Events (`pointerdown/up/cancel/leave`) и `click` для
  клавиатуры/AT; без полифилов и без отдельной ветки mouse/touch. Если
  `PointerEvent` недоступен, элемент управления остаётся скрытым (без
  «мёртвой» кнопки), форма работает.
- **B.** Добавить fallback на `mousedown/mouseup` + `touchstart/touchend`.
  Плюс: старые браузеры. Минус: больше кода и краевых случаев (дублирование
  событий, touch-синтетические клики), при текущей аудитории не оправдано.
- **C.** Поддержка IE11/старых мобильных. Минус: несовместимо с современным
  стеком и стоимостью; не рекомендую.

**Вопрос к человеку:** подтверждаем A (evergreen + Pointer Events, без
полифила, graceful degradation)?

## Нефункциональные требования и риски

### Безопасность

- `SecretKey` и производные ключи **не логируются**, не отправляются по сети,
  не сохраняются в storage/cookie/URL/буфер обмена; новые лог-вызовы со
  значением ключа запрещены.
- Серверный HTML поля остаётся `type="password"`; показ — только локальное
  изменение `type` в рантайме. Запрещено реализовывать «маскирование» через
  CSS/`type="text"`, потому что это меняет поведение автозаполнения и повышает
  риск утечки.
- Не ослаблять `Cache-Control: no-store`, CSRF, rate limiting, проверку срока,
  валидацию. Не добавлять ключ в `data-*`-атрибуты, `title`, `aria-*`.
- Остаточный риск: пока ключ виден, его можно увидеть на экране/сфотографировать.
  Мера — автоскрытие при отпускании/прерывании, отсутствие режима «показать
  навсегда», отсутствие сохранения состояния.
- Никакой аналитики/телеметрии взаимодействия с элементом.

### Доступность (ориентир — WCAG 2.1 AA)

- Роль/имя/значение: нативная `button type="button"`, доступное имя на
  русском, `aria-controls` на поле, `aria-pressed` отражает видимость; иконка
  `aria-hidden="true"`; без `title` как единственного имени.
- Клавиатура: достижимость `Tab`, видимый focus-ring, `Space`/`Enter`,
  отсутствие keyboard trap; `Escape` скрывает.
- Touch target: не меньше 40×40 CSS px (рекомендуется 44×44), без уменьшения
  высоты поля; достаточно контрастная иконка (наследует `currentColor`,
  видима в `forced-colors`).
- Нет обязательного «удержания» для клавиатуры/AT (Q3-A); состояние
  озвучивается скринридером.
- Анимация отсутствует или уважает `prefers-reduced-motion`; переключение не
  вызывает layout shift.

### Производительность и совместимость

- Скрипт без зависимостей, `defer`, малый объём; один делегированный
  обработчик; без сети, без polling, без `setInterval`.
- Переключение `type` не должно приводить к заметному layout shift/скачку
  вёрстки; значение и каретка сохраняются.
- Браузеры — по Q8-A. `PointerEvent` и `hidden` поддерживаются целевой
  матрицей; при отсутствии — graceful degradation (AC6).
- Touch: не блокировать прокрутку, не подавлять контекстное меню глобально —
  только в пределах элемента и только на время взаимодействия.

### Локализация и UI

- Все доступные имена/подсказки — на русском, в терминологии `SecretKey`
  («Показать секретный ключ» / «Скрыть секретный ключ»), без «пароля».
- Визуально — иконка, без обязательного видимого текста; `title`/tooltip не
  обязателен.
- Не менять существующие label, placeholder, help и тексты ошибок.

### Архитектура и границы

- Изменения — только Presentation (шаблоны/form-тема/ассеты) и тесты/доки;
  `Domain`/`Application` не импортируют Symfony/Twig/JS-понятия; deptrac — 0
  нарушений.
- Новых модулей, портов, доменных событий, миграций и зависимостей нет.
- Имена в новом коде — `SecretKey`/`secret-key-visibility`, не `password`/
  `paste` (легаси wire-имена `create_paste`/`unlock_paste` сохраняются).

### Тестируемость и качество

- Functional-тесты расширяются проверками AC1 (разметка, атрибуты, `hidden`,
  неизменные контракты); существующие тесты не переписываются под новое
  поведение.
- `make qa` (cs-check, PHPStan L10, deptrac, PHPUnit) — зелёный; новых
  `@phpstan-ignore` без причины/даты нет.
- Ручной чек-лист в `plan.md`: pointer, touch (iOS/Android), клавиатура,
  скринридер, no-JS, браузерная матрица, проверка сети/консоли/storage.
- Обратимость: изменение локально в Presentation/ассетах; откат — revert без
  миграций и побочных эффектов.
