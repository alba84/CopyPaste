# Артефакты задач

Здесь живёт рабочая документация по каждой задаче. Это «журнал» пайплайна:
аналитик, архитектор, тестировщик и ревьюер оставляют артефакты, по которым
работают следующие агенты и человек.

## Идентификатор задачи

Формат: `NNN-slug`, где `NNN` — трёхзначный номер по порядку, `slug` — краткое
английское имя в kebab-case.

Пример: `docs/task/001-extract-create-secret/`.

## Структура

```text
docs/task/<id>/
├── requirements.md   # аналитик   — что и зачем, критерии приёмки
├── plan.md           # архитектор — как, по шагам, с тест-планом
├── review.md         # ревьюер    — вердикт по соответствию и качеству
└── notes.md          # любой      — свободные заметки, если нужно
```

## Владельцы и читатели

| Артефакт | Создаёт | Читают | Когда |
|---|---|---|---|
| `requirements.md` | аналитик | человек (гейт G1), архитектор, ревьюер | начало задачи |
| `plan.md` | архитектор | человек (гейт G2), разработчик, тестировщик, ревьюер | после G1 |
| `review.md` | ревьюер | оркестратор, человек (гейт G3) | после QA |
| `docs/UBIQUITOUS_LANGUAGE.md` | аналитик | все | при новых терминах |
| `docs/adr/NNNN-*.md` | архитектор | все | при изменении стандартов |

## Гейты (человек в цикле)

- **G1 — требования.** После `requirements.md`. Человек подтверждает объём,
  критерии приёмки и термины. Без подтверждения пайплайн не идёт дальше.
- **G2 — план/архитектура.** После `plan.md` и, отдельно, при изменении
  стандартов (ADR). Человек утверждает подход.
- **G3 — перед коммитом.** После ревью. Человек смотрит diff, запускает
  `make qa` (или доверяет отчёту QA) и коммитит сам. Агенты не пушут.

Между гейтами пайплайн работает автономно: разработка → тесты → QA → ревью с
циклом исправлений. Оркестратор эскалирует человеку досрочно при
неоднозначности, рисках безопасности, миграциях, изменении публичного API или
стандартов.

## Шаблон requirements.md

```markdown
# <id>: <Название>

## Контекст и проблема
## Пользовательская цель
## Объём (in scope)
## Вне объёма (out of scope)
## Доменные термины (новые/уточнённые)
## Критерии приёмки (Given–When–Then)
## Открытые вопросы (и ответы человека)
## Нефункциональные требования и риски
```

## Шаблон plan.md

```markdown
# План: <id>

## Связь с требованиями
## Затрагиваемые модули и слои
## Изменение модели/контрактов (агрегаты, VO, порты)
## Тест-план
- unit:
- application:
- functional:
## Пошаговый план реализации
## Миграции БД
## Влияние на стандарты (ADR, если нужно)
## Риски и обратимые шаги
## Definition of Done для задачи
```

## Шаблон review.md

```markdown
# Ревью: <id>

## Вердикт: approved | changes-requested
## Соответствие requirements.md
## Соответствие plan.md
## Соответствие docs/ARCHITECTURE.md и docs/CONVENTIONS.md
## Найденные проблемы (блокирующие / неблокирующие)
## Протечки абстракций между слоями
## Тестовое покрытие
## Замечания по безопасности
```
